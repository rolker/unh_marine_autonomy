# World store: Roland's high-level goals (his words, 2026-10-02)

Context: Roland asked whether "we need to spell out the high level goals in order to anchor the bits of the design.
It might be that the design (I mean how I think about it, not necessarily the implementation) needs to be modular so
I can grasp the whole picture at various levels."

Goals as he listed them:
- LIVE: "While collecting data, see new data coming in that day or deployment shown distinctively from previous days'
  collected data. Previous days' coverage should also show up distinctively from older reference data." He finds it
  debatable whether this belongs in the big picture; suspects yes, "due to the camp side needing to display live data
  along with stores data".
- EXPLORE TOGETHER: "Post mission, I want to be able to see and explore the various types of data together in context
  with each other." This summer: sidescan, bathy, backscatter; "the need was to compare a feature identified in one
  product with the data from the other products".
- COMMON STORE FOR PROCESSING: "for implementing existing and implementing new processing techniques that can take
  advantage of the multiple data passes and/or types".
- ONE WORLD: "not need to carve out geographic areas by keeping all the data together so it can be explored like we
  explore the globe with google maps or earth. It's ok to define sub areas for processing and such, but that doesn't
  mean the data needs to live apart."
- AUTOMATIC QUALITY: "automatically process the data enough for assessing its quality and showing gaps".
- FOR ROBOTS: "designed for marine robotics so it can serve as a source of updated navigation data, and also for
  on-board automated quality assessment and coverage planning".
- EXPORT: "Ability to export the raw data to hydrographic formats such as gsf and xtf."

He asked: "Am I missing something? Can we use these high level goals to help figure out which one the design details serve?"

Agent's reply (same day): candidates for missing = corrections without rewriting bags (his first purpose on 10-01),
vector features/contacts, a person's review, more than one machine, known uncertainty. Proposed levels: goals ->
capabilities -> parts -> details. First mapping showed the deferred bookkeeping (per-tile catalog entries,
fingerprints, replicas) anchors to no goal on this list, and LIVE, AUTOMATIC QUALITY and EXPORT have little or no
design behind them. Three questions asked (corrections: goal or means; export raw or corrected; where a person's
review fits). Nothing written to the design document.

## Roland's second pass (2026-10-02, later) — his words

- "to make this stand out and be justified, the primary goal is to make this for marine robotics, so that should be
  the top listed goal. From that falls out the goal of supporting stores on multiple machines, some linked with
  bandwidth limited connections."
- "The corrections part should fall out of a goal to not rewrite the raw files."
- Thought: "before leaving the boat, once a bag file is written, should it be set to read-only?"
- "I don't think data cleaning is a goal, but it might be something we support. I think that can be articulated with
  a non-goal. Replacing the traditional hydrographic processing chain is not a goal."
- "a goal related to its marine robotics focus is to support robot decision making, which includes safe navigation,
  opening the door for vector data, and automated coverage planning, both justifying the need for uncertainties."
- "In practice this past summer, data was always collected on the ros side when deployed, but not always with qinsy.
  qinsy also does not support the garmin sidescan so ros bags were the only recording mechanism we had, so a goal is
  to still support traditional hydrographic processing by having the ability to export to common formats. This works
  around issues such as lack of drivers or lack of personnel to operate the survey side."
- "To support an operational tempo, a goal is to be able to explore the combined data quickly after the deployment in
  order to plan an upcoming deployment that may be next day, or after a few hours of recharging batteries."

Agent's restatement offered back (not yet confirmed by Roland):
1. Built for marine robotics: support robot decision making (safe navigation, automated coverage planning, on-board
   quality assessment). Falls out: uncertainties, vector data, stores on several machines over limited links.
2. Raw files are never rewritten. Falls out: corrections as separate records applied when products are built.
3. Operational tempo: explore the combined data soon after a deployment to plan the next (next day, or a few hours).
   Falls out: automatic processing for quality and gaps; live display; types together; one world.
4. A common store for existing and new processing across passes and types.
5. Support traditional hydrographic processing by export to common formats (GSF, XTF).
Non-goals: replacing the traditional hydrographic chain; data cleaning (may be supported).
Agent's answer on read-only bags: yes, as a guard against accidental in-place rewrites, plus a checksum at close;
not implemented, not filed. Questions asked: where the post-deployment data comes from within "a few hours"; export
as recorded or with known recording faults fixed; robot decisions during an outing or between outings.

## Roland's third pass (2026-10-02) — his words

- "The battery recharging part can be generalized to robot turn-around time."
- "Cleaning marks are still relevant for automatic filters and should still support indicating user or manual cleaning."
- Where post-deployment data comes from: "in practice, we did trickle the full bag files over starlink while the boat
  was still deployed. At the dock, we did have the option to copy the files over a faster wifi connection. Such
  technology can change, so keeping the details generic in the goal seems right to me."
- Export as recorded vs with faults fixed: "both paths can be useful and should be supported I think."
- Robot decisions: "same outing, essentially modernizing and improving on the ideas behind manda_coverage."

Agent's notes: manda_coverage (core_ws; ROS port of Damian Manda's MOOS planner, UNH MS thesis 2016) subscribes to
ping point clouds + odometry and plans the next line from the swath it just saw; it reads no store. Same-outing
decisions mean the boat builds its store as it surveys and a planner reads it while it is written, so the pipeline
needs an incremental path beside the site rebuild. Agent proposed writing the goals page into the design document
(awaiting Roland's yes).

## Roland's fourth pass (2026-10-02) — his words

- "'support live robot decision making' eliminates the need to say on the same outing."
- Export: "a nuance to mention is to be able to export the data as recorded, with filters applied, but without
  further corrections."
- Manual cleaning: "I'm not sure how to weigh manual cleaning support. I don't want to have to do manual cleaning, but
  it might be required to make the data usable for purposes such as target searching or marine archeology."
- Scope: "To set a broad scope, but not too broad, this is aimed at marine mapping robots. Seafloor mapping from the
  surface is the case we start with, but midwater targets (as vector data probably) from watercolumn data or
  underwater vehicles should not be precluded from using this. They don't need to be designed in, we just need to
  keep some of the ideas flexible enough, such as not assuming nav is from RTK GPS. Vector support already covers
  midwater targets."
- Live: "the current implementation has cube reading the live data to produce the live tiles, so no reading from the
  bag files in that scenario. How much the stores play a role in the live, on boat scenario is still up for debate I
  guess."

Agent's positions offered: a mark records who or what made it (filter + version, or a person), so manual marks cost
nothing in the record and only the hand-cleaning tool is left out; marks keyed to the raw sounding identity are what
make "filters applied, no corrections" exportable; on the boat the minimum store role is that the live builder writes
tiles the store's way and everything reads them through the same tile reader (the costmap already reads store tiles
on the boat). Question asked: does a shore rebuild replace the boat's live tiles or sit beside them.

## Live tiles vs rebuilt tiles — Roland, 2026-10-02 (his words)

"For monitoring live coverage, we have a message type and process for transmitting tiles meant for viewing, not for
transferring durable stores data. Also, the live cube process can drop pings, so its output can show gaps that are
not really in the data. I think that's ok as a live viewer, but those drafts should be replaced with tiles from the
full data when practical. So, on the boat side, the tiles might contain the full data ranges (not reduced to a
display only bit rate), but have missing pings. On the operator side, those live tiles suffer from both degradations."

Agent's reading: three kinds of tile for the same place and day — boat live (full values, missing pings), operator
live view (reduced values AND missing pings; arrives as marine_interfaces SonarVisualizationTile messages, a viewing
path), rebuilt from the full recording (complete). Questions asked: is the boat's live tile good enough for the boat
planning its own coverage; is the rebuild from full data wanted on the boat or is it a shore job; are operator view
tiles kept after real tiles exist.

Roland's answers (2026-10-02, his words):
1. Planner on live tiles with dropped pings vs full data: "I think we should support both. Data rates and processing
   availability can both vary."
2. Rebuild on the boat or ashore: "another one that depends. For a while this summer, BizzyBoat was docked overnight
   far from the operator station so all data transfers were over starlink, which charges by usage. In that case,
   independently building surfaces on the boat and at the operator station makes sense. Otherwise, having one host
   build a surface and others being able to copy it rather than all building them would be good when it makes sense."
3. Operator live view tiles: "they can be thrown away once replaced by real tiles, but they should persist between
   restarts of camp for instance. Same on the boat, I think tiles can persist so cube can reload them as needed."

Agent's reading offered back: the design must not fix where a surface is built; a tile says what it was built from
(live stream, possibly with dropped pings, or the full recording); the same build on two machines must be recognisable
as the same so a copy can stand in for a rebuild; live tiles are a local, persistent, replaceable cache on each machine.
Proposed: write this as the first detail section of the design document (awaiting yes).
